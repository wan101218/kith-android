# Kith · 产品设计

> **Kith** —— 古英语 *kith and kin*，意为「亲友与故交」。
> 一个模拟社会的 AI 团应用：你造一个社会，看它自己活起来。

---

## 一、这是什么

Kith 让用户创建一个**自洽的 AI 社会**：设定世界观与剧情走向，放入若干有性格、有关系的人物，
再由一个**旁白 AI** 持续推进剧情 —— 需要新角色时，它会创造一个背景与关系都能和前面剧情
无缝衔接的人，并且按这个人有多重要，自动分配档位合适的模型。

用户既可以像看剧一样旁观（树状图看关系、上帝视角看 NPC 之间说话），
也可以像玩 galgame 一样亲自下场攻略某个人。

### 核心差异点

| 差异点 | 说明 |
|---|---|
| **一个社会 = 一个独立项目** | 每个社会各自一个文件夹，物理隔离，之间无法互相访问；导出即为一份可分享的 JSON |
| **旁白是真正的作者** | 不是提示词模板，而是有职责的智能体：推进剧情、造人、造关系、打分、派模型 |
| **成本可控的多厂商** | 371 个模型带真实价格，按人物重要性自动分档；关键角色用旗舰，路人用最便宜的 |
| **人物是真的在「像人」说话** | 内置 Human Chat Protocol 人格规范，会短句、会口语、会发表情包、会转账 |
| **标签驱动关系** | 给角色打「恋人」，TA 的一切态度、称呼、距离感都会跟着变 |

## 二、信息架构

```
社会列表（Kith）
├── 新建社会
│   ├── 名称 / 剧情走向模板（BL GL BG BZ / 自定义）
│   ├── 世界观描述
│   ├── 剧情走向 + 题材标签
│   ├── 主要人物（可配性格、性别、标签、模型）
│   └── 模型配置（旁白 / 人物默认 / 文生图）
│
├── 社会（主界面）
│   ├── 透明状态栏：人物数 · 关系数 · 累计花费 · Token · 当前章节
│   ├── 关系图（树状 / 链式，可切换）
│   │   ├── 点击次要人物 → 只展示资料
│   │   └── 点击重要人物 → 资料 + 发消息
│   ├── 旁白面板
│   │   ├── 剧情现状（章节 / 概要 / 氛围 / 伏笔 / 最近事件）
│   │   ├── 给旁白的指示
│   │   └── 是否顺带引入新人物
│   ├── 人物管理（增删改）
│   ├── 社会模型配置（旁白 / 人物默认 / 文生图）
│   └── 日志
│
├── 与某人的会话
│   ├── 协议渲染：文本 / 表情包 / 图片 / 转账
│   ├── 发图片（纯文本模型自动走视觉桥接）
│   └── 每条消息的模型与花费
│
└── 设置
    ├── 模型接入点（厂商图标 + 自动填 baseUrl）
    ├── 已保存的模型配置
    ├── 模型目录（在线刷新 / 手动导入 / 恢复内置）
    ├── 视觉桥接
    ├── 旁白行为 / 玩法开关
    └── 界面（主题 / 关系图默认布局）
```

## 三、关键流程

### 1. 关系图：两种布局

社会关系本质是一张**图**而非树（A 是 B 的朋友，B 是 C 的同事，C 又和 A 是邻居），
所以：

- **树状图**：按与「你」的**层级距离**分层。第 0 层是你本人，第 1 层是你的直接关系人，
  第 2 层是他们的关系人。保留了「一眼看出谁离你近」的树状直觉，
  又不会因为环状关系而布局失败。同层内按与上一层的连接强度排序，关系近的排中间。
- **链式图**：按 BFS 顺序把所有人物串成一条正弦波走线，强调关系的传递性 ——
  适合看「A 通过 B 认识 C」这类间接链路。

**点击行为按重要性区分**（产品明确要求）：`LEAD` / `MAJOR` / `SUPPORTING` 档位的人
物可以发消息，`MINOR` / `EXTRA` 只展示资料。

### 2. 旁白推进剧情

用户点「让旁白推进一段」后：

```
社会设定 + 人物表 + 剧情现状
        ↓
   旁白模型（JSON 模式）
        ↓
  ┌─────────────────────────────┐
  │ narrative   给用户看的旁白文本 │
  │ plotUpdate  章节 / 概要 / 氛围 │
  │ beats       刚发生的事        │
  │ hooks       埋下未回收的伏笔   │
  │ newCharacters[]  新人物        │
  │   ├ importanceScore 自评分     │
  │   └ relations[] 与既有人的关系  │
  └─────────────────────────────┘
        ↓
  重要性融合 → 档位 → 模型分配
```

### 3. 新人物如何「无缝衔接」

旁白被明确要求：新人物必须与**现有至少一个人物**建立关系，且背景经历要能解释得通。
落地上做了一层容错对齐：

- `toCharacterId` 解析顺序：**已有角色 id** → **本批次新人姓名** → **已有角色姓名**。
  模型经常把 id 写成名字，硬要求它只输出 id 不现实。
- 解析不出来的关系会被**丢弃并记日志**，而不是产生一条指向空气的连线。
- 如果某个新人物一条关系都没接上，会**明确记一条日志**告诉用户「这个人现在是孤立的」，
  而不是悄悄放一个孤岛进关系图 —— 那正是「无缝衔接」要求的失败情形，必须让用户看得见。

### 4. 重要性评分与模型分配

这是成本控制的中枢。设计原则：**不能只信模型给的分**。

模型有很强的「礼貌性通胀」倾向 —— 你让它给人物打分，它很容易觉得「这个角色也挺重要的」
然后给 70 分。一个人人 70 分的社会，用旗舰模型的成本会迅速失控。

因此最终分数由两部分融合（取加权后较大值，保证结构上明显重要的人不被压下去）：

| 信号 | 权重 | 说明 |
|---|---|---|
| 模型判断 | 0.55 | 它理解剧情语义，知道谁在叙事上有位置 |
| 结构分 | 0.60 | 客观、无法虚报 |

结构分的构成：
- 每有一条关系 +11（最多 4 条起效）
- 强关系（亲密度 ≥ 70）每条 +9（最多 2 条）
- **用户亲手打的标签 +22** —— 你在意的人就是重要的人
- 剧情提及次数 +6/次（最多 3 次）
- 如果挂的全是「点头之交」，整体 ×0.7

分数 → 档位 → 模型：

| 分数 | 重要性 | 档位 | 典型用途 |
|---|---|---|---|
| 85–100 | 核心 | 旗舰 | 主线支柱，长期反复出现 |
| 65–84 | 重要 | 标准 | 有独立戏份与关系网 |
| 45–64 | 配角 | 经济 | 有明确功能位 |
| 25–44 | 次要 | 经济 | 背景人物 |
| 0–24 | 路人 | 经济 | 一次性出场 |

档位 → 具体模型的挑选**按价格分位**而不是硬编码名单 ——
目录一刷新，档位划分自动跟着变，不会出现「名单里的模型下线了但代码还指着它」。

还有一个容易忽略的坑：目录里的模型只有在用户**配置了对应厂商的接入点**时才可用。
所以自动分配不能只按价格挑，必须限定在用户已配好 Key 的厂商范围内，
优先顺序为「旁白所在厂商 → 用户默认人物模型厂商 → 其余已配置厂商」。

### 5. 标签驱动关系

给角色打标签后，标签整段写进该角色的 system prompt：

> **你与 TA 的关系是：恋人**
> · 恋人：TA 是你的恋人。称呼可以亲密，会主动撒娇或吃醋，会关心你的行程，
>   会表达想念。涉及其他人时会有占有欲。
> 你的一切态度、称呼、距离感、主动性，都必须严格符合这个关系。

内置 15 个标签模板（恋人 / 暧昧对象 / 配偶 / 挚友 / 朋友 / 家人 / 同事 / 上司 /
下属 / 对手 / 宿敌 / 师长 / 学生 / 暗恋者 / 陌生人），也可以在编辑器里自由组合。

### 6. 消息闭塞

每个角色一条**独立会话文件**（`chats/{charId}.json`），system prompt 里只出现这个角色
自己的关系与记忆。A 说过的话绝不会漏进 B 的上下文 —— 这是产品明确要求的
「消息也是闭塞的不能串台」。

## 四、协议与人格

Kith 完整实现了 `human-chat-protocol` skill 定义的应用层规范。

### 三个标签

| 标签 | 用途 | 渲染 |
|---|---|---|
| `<sticker emotion="笑哭" />` | 发表情包 | 系统 emoji（46sp）或用户上传的图片 |
| `<chat_image prompt="橘猫晒太阳" style="写实" ratio="3:4" />` | 发图 / 触发生图 | 占位 → 异步生成 → 替换；失败显示原因 |
| `<transfer amount="5.20" to="小明" note="请你喝奶茶" />` | 转账 / 红包 | 卡片，需用户点击「收下」确认 |

解析器比规范更宽容：支持单引号属性、漏掉斜杠的闭合、以及流式输出时的
**半截标签截断保护**（否则 `<sticker emot` 会先闪成文本再变成表情，观感很差）。
解析失败一律降级为纯文本，绝不静默丢弃模型输出的内容。

### 表情包匹配（三级）

1. **精确匹配** — `emotions` 数组里完全等于情绪词
2. **模糊匹配** — 包含关系
3. **兜底** — 系统 emoji，保证界面上永远有东西出现

系统表情用 **emoji 字形**渲染而非预置位图：emoji 在系统字体下就是用户平时在微信里
看到的样子，观感天然是真的，不需要塞一堆位图进包体，也不会出现「画出来的假表情」
那种廉价感。每个情绪词映射多个字形，命中时随机取一个，避免每次都说「笑哭」就发同一张。

### 人格规范

`chat-style-guide.md` 的核心规则被压缩后整段注入 system prompt：

- **句子要短** —— 一条消息一两句话，说完就发
- **用口语** —— 「好的，我来帮你」→「行 / 可以 / 好啊」
- **有情绪** —— 对方倒霉要心疼，报喜要起哄，离谱的事要惊讶
- **可以不完美** —— 用语气词、用省略号、偶尔跳话题
- **长度感** —— 日常闲聊 1–3 句，最多 5 句
- **绝对不要** —— 列 123、用 markdown、每句「哈哈哈」、说「作为一个 AI」、做心理分析

## 五、安全边界

- **转账只渲染卡片，不接入任何真实支付通道。** 用户点「收下」后仅把卡片标记为
  已确认并记一条日志。
- **API Key 只存在本机应用私有目录**（SharedPreferences），不上传任何服务器。
- **默认视觉 Key 是共享额度。** 首次真正触发视觉调用时会提示用户建议换成自己的 Key。
- **删除社会需要二次确认**，并明确列出会丢失的内容，同时建议先导出备份。

## 六、视觉语言

- **墨黑 + 琥珀**：琥珀是唯一强调色，只用在「你 / 当前 / 重要」这些真正需要被看到的地方
- **不启用 Material You 动态取色**：品牌色是所有界面里三级信息的共同语义载体，
  被系统壁纸改掉就失效了
- **厂商图标用「品牌色磁贴 + 字母徽记」**，而不是各家商标位图 ——
  20 多个图标风格无法统一会破坏一致性，而且这套做法能覆盖任意新厂商
  （含用户手填的），颜色由名称哈希派生
- **人物头像用「姓名首字 + 稳定渐变」**：同一个名字永远得到同一套配色，
  用户在关系图和聊天里看到的是同一个视觉身份
- **状态栏透明 + 真实高斯模糊**（`Modifier.blur`，minSdk 33 可直接用），
  滚动时下方内容透出来糊开

### 图标

「Kith 关系星群」：一簇由连线构成的节点群。中心一枚琥珀色节点代表「你」，
外围四枚白色节点沿一条开放链依次相连代表社会关系链，中心与所有外围节点相连 ——
你与每一个人都有联系。

全部收在自适应图标中心 r≈31 的安全圆内（系统蒙版安全区 r=33），
48px 下仍可辨识。
